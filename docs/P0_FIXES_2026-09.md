# P0 Data-Integrity Fixes — September 2026

Four verified P0 data-integrity bugs, each reproduced with a failing regression
test before the fix (TDD). All four are silent data-loss / data-corruption
issues: nothing errors visibly, but user trades/notes are destroyed or trades
are booked wrong.

| # | Area | Symptom | Root cause | Fix |
|---|------|---------|-----------|-----|
| 1 | Cloud sync (frontend) | Local trades/notes silently wiped | Pull overwrote local with `cloudData.trades ?? []` even when cloud lacked the field | Only overwrite when cloud has a non-empty array |
| 2 | Journal push (frontend) | Cloud notes wiped when a trade is edited | One push call passed a hardcoded `notes: []` | Send current notes (storage fallback); fix the call site |
| 3 | Webhook retries (backend) | Duplicate events/trades on retry | External `order_id` was parsed but never persisted or de-duplicated | Persist `order_id` + `(user_id, order_id)` unique index + idempotent ingest |
| 4 | Pine parsing (backend) | `exit_long` opened a phantom long | Message parser checked `long` (buy) before `exit` | Exit/close take precedence over direction words |

All four were treated as hunches and reproduced before fixing.

---

## Bug 1 — Cloud pull must not wipe local trades/notes

**File:** `frontend/app/utils/cloudSync.ts` (`initJournalSync`, `forceSyncFromCloud`)

**Repro:** A cloud `journal` record exists but is missing `trades`/`notes`
(older client wrote a partial payload, or a settings-only push happened), or the
fields are present but empty. On the next login / "Sync from Cloud", the code ran:

```ts
const cloudTrades = cloudData.trades ?? []   // undefined → []
lsSet(TRADES_KEY, cloudTrades)               // wipes local trades
```

Because `cloudData` itself was truthy, the `?? []` fallback overwrote
`localStorage` with an empty array, destroying the user's journal.

**Fix:** Overwrite local only when the cloud actually has data — the same guard
already applied to `templates`, `propFirmAccounts`, etc.:

```ts
if (Array.isArray(cloudData.trades) && cloudData.trades.length > 0)
  lsSet(TRADES_KEY, cloudData.trades)
if (Array.isArray(cloudData.notes) && cloudData.notes.length > 0)
  lsSet(NOTES_KEY, cloudData.notes)
```

Legitimate cloud data still overwrites local (source-of-truth path intact); a
missing/empty cloud field no longer nukes local.

**Tests:** `frontend/tests/unit/cloudSync.test.ts` — preserves local on
missing fields, preserves local on empty arrays, still overwrites with real
cloud data.

## Bug 2 — Journal push must send current notes, never hardcoded `[]`

**File:** `frontend/app/journal/page.tsx` (trade-edit auto-save) +
`frontend/app/utils/cloudSync.ts` (`debouncedSyncJournal`)

**Repro:** Editing a trade auto-saves and pushes the journal:

```ts
debouncedSyncJournal(updated, [])   // notes hardcoded to []
```

The push writes the whole `journal` payload to the cloud with `notes: []`, so
every note is wiped in the cloud. Combined with Bug 1 this was doubly
destructive — the empty cloud notes would then propagate back to other devices.

**Fix:** Make `notes` optional in `debouncedSyncJournal`; when omitted it reads
the user's **current** notes from `localStorage` (notes are always persisted
there via `saveNotes`), mirroring the existing `templates` fallback. The call
site now omits notes:

```ts
debouncedSyncJournal(updated)   // sends current notes, never []
```

**Tests:** `frontend/tests/unit/cloudSync.test.ts` — omitted notes send current
stored notes (not `[]`); explicitly provided notes are respected.

## Bug 3 — Webhook retries must be idempotent

**Files:** `backend/routes/webhooks.js`,
`database/migrations/018_webhook_event_idempotency.sql` (+ rollback)

**Repro:** TradingView/NinjaTrader retry a webhook on timeout (and proxies
can replay it). The receiver parsed `order_id` but never persisted or checked it,
so each delivery inserted a new `webhook_events` row and a new `webhook_trades`
row — a single fill became two (or more) trades, corrupting P&L.

**Fix:** Idempotency keyed on the persisted external `order_id`, backed by a
DB uniqueness constraint:

- New `ingestAndMatch()` centralizes event ingestion for both the TradingView
  and NinjaTrader receivers: it checks for an existing event with the same
  `(user_id, order_id)` and skips (no new event, no new trade) on a match.
- The external `order_id` is persisted on `webhook_events`.
- A partial unique index on `(user_id, order_id)` is the race-safe backstop: a
  concurrent retry that wins the insert race causes the loser to hit a unique
  violation, which is swallowed as a duplicate.
- Token `trade_count` is not incremented for duplicates.

**Placeholder safety:** TradingView strategy alerts often set `order_id` to a
non-unique placeholder (the direction word `Long`/`Short`, or the action).
`idempotencyKeyFor()` treats those as *not* an idempotency key (stored as `NULL`,
excluded by the partial index), so distinct trades that share a placeholder are
never collapsed. Only genuine per-fill order ids de-duplicate.

**Event-level, not trade-level:** De-duplication is enforced on `webhook_events`
(one delivery = one event), never on `webhook_trades`, because a single exit
event can legitimately produce several trade rows (multi-contract / partial
closes) that share one `order_id`.

**Tests:** `backend/tests/webhookIdempotency.test.js` — first ingest creates one
event+trade; retries are no-ops; distinct ids each journal; placeholders and
empty ids never de-dup; a racing unique violation is swallowed;
`idempotencyKeyFor()` unit coverage.

### Migration & rollback safety (Bug 3)

Migration: `database/migrations/018_webhook_event_idempotency.sql`
Rollback:  `database/migrations/018_webhook_event_idempotency_rollback.sql`

**Forward safety**
- `ALTER TABLE webhook_events ADD COLUMN IF NOT EXISTS order_id VARCHAR(100)` is
  nullable with no default → **no table rewrite, no backfill**; existing rows get
  `order_id = NULL`.
- The unique index is **partial** (`WHERE order_id IS NOT NULL`). Every existing
  row has `order_id = NULL`, so the index build **cannot conflict** with
  historical data — it will always succeed on live tables.
- In prod, build the index with `CREATE UNIQUE INDEX CONCURRENTLY` (the
  commented form in the migration) to avoid holding a write lock. The plain
  `CREATE UNIQUE INDEX` form is for transactional migration runners / fresh
  installs.
- Idempotent/re-runnable: `IF NOT EXISTS` on both the column and the index.

**Backward compatibility**
- Old receiver code that does not send `order_id` simply writes `NULL` — fully
  compatible with the new column and index.
- New receiver code is defensive: it only queries/writes `order_id` when a real
  external id is present, and swallows unique violations, so it behaves correctly
  whether or not the migration has been applied (before the migration, no
  duplicates are found and inserts proceed as before).

**Rollback safety**
- `DROP INDEX IF EXISTS uniq_webhook_events_user_order;` then
  `DROP COLUMN IF EXISTS order_id;` — instant and **non-destructive**. Only the
  retry-dedup metadata is removed; all `webhook_events` and `webhook_trades`
  rows are untouched. After rollback the receiver falls back to its previous
  (non-idempotent) behavior with no errors.
- Deploy order is flexible: because both old and new code tolerate the column's
  presence/absence, the migration and the code deploy can go in either order.

## Bug 4 — Pine `exit_long` must parse as exit/sell, not buy

**File:** `backend/routes/webhooks.js` (`parsePayload`)

**Repro:** A Pine `alert_message` of `exit_long` was parsed as a **BUY**:

```js
if (msg.includes('entry') || msg.includes('buy') || msg.includes('long')) derivedAction = 'buy';
else if (msg.includes('exit') || msg.includes('sell') || msg.includes('short')) derivedAction = 'sell';
```

`exit_long` contains `long`, so the first branch matched and it became a buy —
opening a phantom long instead of closing the real position.

Confirmed before fix:

```
entry_long => buy   exit_long => buy (WRONG)   entry_short => buy   exit_short => sell
```

**Fix:** Exit/close semantics take precedence over the direction words:

```js
if (msg.includes('exit') || msg.includes('close')) derivedAction = 'sell';
else if (msg.includes('entry') || msg.includes('open')) derivedAction = 'buy';
else if (msg.includes('sell') || msg.includes('short')) derivedAction = 'sell';
else if (msg.includes('buy') || msg.includes('long')) derivedAction = 'buy';
```

Now `exit_long`/`close_long` → sell, `entry_long` → buy, `exit_short` → sell,
bare `long`/`short` → buy/sell (unchanged).

**Tests:** `backend/tests/webhook-tradingview.test.js` (TV-1.11–TV-1.15).
